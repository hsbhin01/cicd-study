# 00. CI/CD 큰 그림

## 왜 필요한가?
CI/CD가 없으면 보통 이런 문제가 생깁니다.
- "내 컴퓨터에서는 되는데요" → 빌드 환경이 사람마다 다름
- 여러 사람의 변경을 한참 뒤에 합치다가 충돌과 버그가 몰려서 터짐 (merge hell)
- 배포가 수작업이라 느리고, 무섭고, 실수가 잦음 → 배포를 미루게 됨 → 한 번에 바뀌는 양이 커져 더 위험해짐

CI/CD의 핵심 아이디어는 **작게, 자주, 자동으로** 입니다.

## 세 가지 용어
| 용어 | 뜻 | 자동화 범위 |
|---|---|---|
| **CI** (Continuous Integration) | 변경을 자주(하루 여러 번) 메인 브랜치에 합치고, 합칠 때마다 자동으로 빌드와 테스트 | 코드 → 검증된 빌드 |
| **Continuous Delivery** | 언제든 배포할 수 있는 상태의 산출물을 항상 준비. 운영 배포는 **사람이 버튼을 눌러** 승인 | → 배포 가능한 산출물 (+ 스테이징 배포) |
| **Continuous Deployment** | 테스트를 통과하면 운영까지 **사람 개입 없이** 자동 배포 | → 운영 배포까지 전부 |

> "CD"는 문맥에 따라 Delivery일 수도, Deployment일 수도 있습니다. 차이는 **운영 배포 직전에 사람의 승인이 있느냐**입니다.

## 파이프라인 단계
```
 commit ──► build ──► test ──► package ──► release ──► deploy
  (git)    (의존성,   (lint,   (Docker    (레지스트리  (dev → stage
           컴파일)    unit,    이미지)     에 태그로     → prod)
                     통합)                 저장)
 └──────────── CI ────────────┘└─────────── CD ──────────────┘
```
- 각 단계는 **품질 게이트(gate)**입니다. 실패하면 다음 단계로 가지 않습니다.
- 앞 단계일수록 빠르고 싸야 합니다. 그래야 실패를 빨리 알 수 있습니다 (fail fast).

## 핵심 개념
- **산출물(artifact)**: 빌드 결과물. 이 스터디에서는 Docker 이미지입니다.
- **환경(environment)**: dev / staging / prod. 같은 산출물이 차례로 승격(promote)됩니다.
- **빌드는 한 번, 배포는 여러 번 (Build once, deploy many)**: 환경마다 다시 빌드하지 않습니다. 같은 이미지를 쓰고 **설정만** 바꿉니다(환경변수, ConfigMap). 그래야 스테이징에서 테스트한 것과 운영에 나가는 것이 완전히 같습니다.
- **불변성(immutability)**: 한 번 만든 이미지 태그(예: git SHA)는 덮어쓰지 않습니다.
- **모든 것은 코드로**: 파이프라인(`.github/workflows/*.yml`), 인프라(`k8s/*.yaml`)도 git으로 관리합니다.

## 이 스터디의 전체 흐름 (최종 목표)
```
개발자 push ─► GitHub Actions(CI): lint + test
                   │ (main 머지 시)
                   ▼
             Docker 빌드 → GHCR에 push (태그 = git SHA)
                   │
                   ▼
             k8s/ 매니페스트의 이미지 태그를 바꾸는 커밋
                   │
                   ▼
   로컬 kind 클러스터의 ArgoCD가 git 변경을 감지 → 자동 sync(배포)
```
